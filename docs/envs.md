# Running envs

Each directory under `tf/env/<env>/` is a separate Terraform root with its own state.

## Tools and credentials

- **Terraform** ≥ 1.3 (the `main` modules use `optional()` object attributes).
- **AWS**: the AWS CLI v2 with a profile that can manage the resources; state is in the
  `ch-tlc-state` bucket (us-west-1). With SSO: `aws sso login --profile <p>` then
  `export AWS_PROFILE=<p>`. Check with `aws sts get-caller-identity` before planning.
- **GCP**: `gcloud auth application-default login`.

## Workflow

```bash
cd tf/env/<env>/<unit>
# write terraform.tfvars if the env uses namespace.tf (values below)
terraform init          # again after any module source or provider change
terraform plan -out plan.tfplan
terraform apply plan.tfplan
terraform output        # sensitive outputs: terraform output -raw <name>
```

Read the plan before applying: a module version change or a rename inside a module shows up as
destroy + create (see [versioning.md](versioning.md) §"Moving an env to a newer version").

`terraform.tfvars` is not committed. Envs that use `namespace.tf` list the values they need below.

## Apply order

Some envs read what another env created; apply the producer first.

| Env | Needs first |
|---|---|
| `prod/chapi` | `prod/ecr` applied and `prod-usw1-chapi:latest` pushed |
| `prod/process` | `prod/ecr` applied and a `prod-usw1-process` image pushed |
| `prod/hello_world/service` | `prod/hello_world/network` |

## prod/ecr

Image repositories for the AWS services: `chapi` and `process`, both on ecr `main`. No tfvars
(defaults in `terraform.tf`). Output `process_repository_url` is where process images are pushed.

chapi moved from ecr `v1` to `main` because AWS rejects v1's policy (its second statement has no
Principal: `Invalid repository policy provided`); the live policy had been set by hand. chapi sets
`expire_untagged = false`: `l-prod-chapi` ran digest `sha256:6f7b3c…`, which lost its `latest` tag
when a later image was pushed. The function has since been destroyed, so that reason no longer
holds.

## prod/chapi

The chapi Lambda (lambda `v1`) running `prod-usw1-chapi:latest`. No tfvars. **Destroyed**
(`terraform destroy`, 4 resources: function `l-prod-chapi`, its role, log policy and attachment);
its state is empty. The `prod-usw1-chapi` repository (in `prod/ecr`) and the
`/aws/lambda/l-prod-chapi` log group (created by Lambda, not Terraform) remain.

## prod/vpc

A standalone VPC + subnet + security group from the `v1` modules. No tfvars.

## prod/process

The process-api service (the `cnc` repo, `svc/process`): an HTTP API over Postgres.

**Creates**: a VPC (`vpc_cidr`), two private subnets in two AZs, a service security group, a DB
security group open on 5432 to the service group only, a private Postgres 16 instance
(`prod-usw1-process`), and the container Lambda `l-prod-process` attached to the VPC with a public
function URL. The function URL uses auth `NONE`; the service itself requires
`Authorization: Bearer <key>` on every request.

**Provider**: aws `~> 6.0` (lambda `main` needs it; see [modules.md](modules.md) §aws/lambda). The
other AWS envs are still on 5.x.

**Deployed**: function URL `https://sfvsmnuz54txdbdjchoo5pp7bq0ctirm.lambda-url.us-west-1.on.aws/`,
running image tag `20260923-4`.

**terraform.tfvars**:

```hcl
env               = "prod"
reg               = "us-west-1"
shreg             = "usw1"
tag               = "process"
vpc_cidr          = "10.40.0.0/16"
image_tag         = "20260923-4"   # the tag last pushed and deployed
bootstrap_company = "all"    # the root account: the first user, root
bootstrap_user    = "root"
```

**Deploy**:

1. `prod/ecr`: `terraform apply` (creates `prod-usw1-process`).
2. Build and push the image from the cnc repo (the image must be `linux/amd64`, matching the
   function's `x86_64` architecture, and carries the AWS Lambda Web Adapter extension that
   forwards function-URL requests to the server on :8080):
   ```bash
   make docker-process
   aws ecr get-login-password --region us-west-1 | docker login --username AWS --password-stdin <account>.dkr.ecr.us-west-1.amazonaws.com
   docker tag process-api <process_repository_url>:<image_tag>
   docker push <process_repository_url>:<image_tag>
   ```
3. `prod/process`: `terraform apply`.
4. From the cnc repo, `scripts/process-api-import-root.sh`: it moves the bootstrap key into
   `~/.ai3d/credentials/all/root` (never printed) and rotates it, then
   `scripts/process-api-account.sh ai3d tlc` opens the daily account. Credentials live only in
   `~/.ai3d`; see the cnc doc `tasks/process-v2/api/process-api.md` §"Credentials".

**Updating the code**: push a new image tag, set `image_tag` to it, `terraform apply`. Re-pushing
the same tag does not change the function (it resolved the image at deploy time).

**Secrets**: the DB password and the bootstrap key are generated by Terraform, kept in the state
(S3), and passed to the function as environment variables. The service seeds only its root
account (`all/root`) from the bootstrap key; `scripts/process-api-import-root.sh` then moves that
key into `~/.ai3d` and rotates it, so the bootstrap value in state and the function env is dead
(the service treats a revoked bootstrap key as already provisioned on restart). Do not print
`terraform output bootstrap_key`: every other key is issued by the service and written straight
into `~/.ai3d/credentials/<company>/<user>` by the cnc scripts.

**Deleting**: the DB has deletion protection and takes a final snapshot. Set
`deletion_protection = false` on the `db` module and apply before a `terraform destroy`.

**Rebuilding the DB (drops all data)** — used when the service's schema changes in
place (nothing released, so `000001_init` is edited rather than migrated):

1. Push the new image tag.
2. Add `deletion_protection = false` to the `db` module in `db.tf`; `terraform apply`
   (in-place).
3. `terraform apply -replace=module.db.aws_db_instance.this -var image_tag=<new tag>` —
   the DB replacement and the image roll must land in **one** apply: an old image
   cold-starting against the fresh DB would install the old schema first.
4. Set `image_tag` in `terraform.tfvars`, remove the `deletion_protection` line,
   `terraform apply` (the plan shows only protection going back on).

After step 4 run `scripts/process-api-import-root.sh` (cnc repo) to move the new root key into
`~/.ai3d` and rotate it, then re-open the daily account (`scripts/process-api-account.sh ai3d tlc`).
The service re-seeds its bootstrap tenant (`all/root`, the root user) on the first cold
start. Step 3's delete takes the final snapshot `prod-usw1-process-final`; that
snapshot now exists (from the 2026-09-23 rebuild), so a further replace fails until
it is deleted (`aws rds delete-db-snapshot --db-snapshot-identifier
prod-usw1-process-final`) or kept under another name.

## prod/hello_world

A GCP Cloud Run demo: `network` (gcp/iap `v1`, currently empty) and `service` (two cloudrun `v1`
services, a proxy in front of the app). tfvars: `tag`, `env`, `region`, `project_id`, `company`,
`service_name`, plus `bucket_name`, `db_connection` for `service` and `project` for `network`.
